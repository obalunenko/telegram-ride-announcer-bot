# Bug Report: Session Is Bound to the First Chat Forever

**Type**: Spec conflict
**Severity**: High
**Feature**: 001-sessions-lifecycle
**Reported**: 2026-11-15
**Status**: Patched
**Patched**: 2026-11-15

## Description

A user has exactly one session, keyed by their Telegram ID, and the session
keeps the chat ID of the user's first message. When the same user later
writes in another chat, the bot loads that session and replies, announces,
and pins in the first chat. A user who first talks to the bot privately can
never announce a trip in a group.

Decision: keep one session and one dialog state per user and chat. Each chat
has its own dialog, and replies always go to the chat the user writes in.

## Root Cause Analysis

The original design assumed one conversation per user. Constitution 1.0.x
recorded it ("One session exists per user ... keeps the chat ID of that
message"), so this is a requirement change, not a coding error.

## Recommended Fix

1. Key `sessions` by user and chat; key the dialog state uniqueness by user
   and chat; load the state through the session's `StateID`.
2. Pass the chat ID to `ops.GetSession`, `ops.CreateSession`, and
   `ops.DeleteSession`; `setSessionMiddleware` uses the chat of the message.
3. Amend constitution principle III (MINOR).
4. Test two chats of one user and the repository keys.
