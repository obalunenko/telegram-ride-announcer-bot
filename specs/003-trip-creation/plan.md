## Summary

`/newtrip` puts the session into `StateNewTrip`, and `createTrip` dispatches
each message by the session state to one step function. The first step
creates an empty draft trip in the trips repository; each later step updates
one field through `ops.UpdateTrip`, advances the state, and calls
`replyInTrip`, which saves the session before it sends the prompt. The last
step either soft-deletes the draft or sends the rendered trip card and pins
it.

## Technical Context

**Language/Version**: Go 1.27, single module
`github.com/obalunenko/telegram-ride-announcer-bot` with committed `vendor/`.

**Primary Dependencies**: telego (`SendMessage`, `PinChatMessage`,
`telegoutil` reply keyboards), gofrs/uuid (trip IDs), `text/template`.

**Storage**: In memory: `internal/repository/trips` (map by trip ID with
soft delete through `DeletedAt`); the draft trip ID is kept in the user's
dialog state (001).

**Testing**: `TestService_CreateTrip` (table-driven failures for every step
with failing repository, renderer, and Bot API stubs),
`TestService_PublishTrip` and `TestService_CancelTrip` (full dialogs against
`internal/telegram/telegramtest`), new-trip cases in `TestHandlers_Failure`
and `TestHandlers_NoSession`, and `TestTemplates_Trip` with `trip.golden`.

**Target Platform**: Long-running bot binary and Docker image. CGO disabled.

**Project Type**: Telegram bot, one binary with layered `internal/` packages.

**Performance Goals**: N/A; none established.

**Constraints**: Save the session before each prompt; only the creator can
finish their draft trip. Dates and times use the time zone from
`service.WithLocation` (`RIDE_ANNOUNCER_TIMEZONE`, default `UTC`); the
service clock (`Service.now`) is replaced in tests (BUG-004).

**Scale/Scope**: About 700 lines; one command, five dialog states, three
outcomes (publish, cancel, failure).

## Design Decisions (as built)

1. **Draft trip from the first step**: `startTrip` creates an empty trip so
   every later step only updates one field, and the draft survives between
   messages through the dialog state.
2. **Save before prompt**: `replyInTrip` saves the session, then sends the
   message, so the next answer always finds the new state.
3. **Routing**: ~~`newTripHandler` resets to `StateNewTrip` only when the user
   is not in a trip state; `textHandler` routes text in any trip state to
   `newTripHandler`;~~ `newTripHandler` always calls
   `resetDialog(ctx, sess, StateNewTrip)`, which discards an unfinished draft;
   `textHandler` routes text in any trip state to `tripAnswerHandler`;
   `cancelHandler` calls `resetDialog(ctx, sess, StateStart)` (BUG-003);
   `createTrip` switches on the state.
4. **Confirmation**: ~~exact `no` cancels; every other answer publishes.~~
   `yes` publishes and `no` cancels, ignoring case and surrounding spaces;
   any other answer is asked again with `confirmKeyboard()` (BUG-002).
5. **Publish order**: update the trip (completed; stored since BUG-001), check the creator, render
   the card, reset the state, save the session and send the announcement,
   then pin it. A failed pin is logged and explained with `msgPinFailed`;
   publishing still succeeds (BUG-005).
5a. **Step failures** (BUG-005): `runTripStep` in `trips.go` runs
   `createTrip` and replies with `replyError` when it fails; steps fail
   before they save the next state.
6. **Date and time** (BUG-004): the date step stores the start of the day,
   the time step replaces it with the start; both use the service time zone
   and reject the past. `main` embeds `time/tzdata` because the Docker image
   has no zone database.
7. **Cancel**: soft-delete the draft (`DeletedAt`), so lookups and lists skip
   it.
